Lab guide 10

SELinux, SSH Keys, and Default Permissions

Work with SELinux modes, labels, ports and booleans, verify SSH keys, and control default permissions.

4-5 hours Week 9 complete
Before you start
  • Week 9 complete
  • Both machines reachable
  • A snapshot before you start
  • Use a VM console for network, boot and storage changes. Commands are guest commands, not macOS commands.
  • Examples use shea; substitute your configured account consistently. Follow the weeks in order; shell variables must be recreated after reboot.
  • Take a snapshot of both machines. You will break things on purpose.

1. Modes

Enforcing blocks and logs. Permissive only logs. Disabled does neither - and is never the right answer on the exam.

Check and switch at runtime
getenforce
sestatus
sudo setenforce 0
getenforce
sudo setenforce 1
getenforce
Make the mode persistent
sudo cat /etc/selinux/config | grep -v '^#'
sudo sed -i 's/^SELINUX=.*/SELINUX=enforcing/' /etc/selinux/config
grep '^SELINUX=' /etc/selinux/config
Worth knowing

setenforce changes the current mode only. The file is what applies at boot. A task that says 'SELinux must be enforcing' means both.

2. Read contexts

SELinux contexts are user:role:type:level. The third field is the type.

Install inspection tools
sudo dnf install -y policycoreutils-python-utils audit
Files, processes, ports, and users
ls -Z /var/www/html 2>/dev/null || sudo mkdir -p /var/www/html && ls -Zd /var/www/html
ps -eZ | grep sshd | head -3
id -Z
sudo semanage port -l | grep -w http_port_t

3. Fix a context the right way

This is the classic exam scenario: content served from a non-default location.

Set up a web server with content in the wrong place
sudo dnf install -y httpd
sudo systemctl enable --now httpd
sudo firewall-cmd --permanent --add-service=http && sudo firewall-cmd --reload
sudo mkdir -p /srv/mysite
echo '<h1>Lab site</h1>' | sudo tee /srv/mysite/index.html
ls -Zd /srv/mysite
Point httpd at it and watch it fail
sudo tee /etc/httpd/conf.d/rhcsa-mysite.conf >/dev/null <<'EOF'
<Directory "/srv/mysite">
    AllowOverride None
    Require all granted
</Directory>
EOF
sudo sed -i 's|^DocumentRoot .*|DocumentRoot "/srv/mysite"|' /etc/httpd/conf/httpd.conf
sudo apachectl configtest
sudo systemctl restart httpd
curl -s -o /dev/null -w '%{http_code}\n' http://localhost/
sudo journalctl -t setroubleshoot --no-pager | tail -5
sudo ausearch -m AVC -ts recent 2>/dev/null | tail -20
Fix it permanently with semanage plus restorecon
sudo semanage fcontext -l -C
# New exercise path, no previous rule:
sudo semanage fcontext -a -t httpd_sys_content_t '/srv/mysite(/.*)?'
# On a repeated run, use -m for an existing incorrect rule, or leave a correct rule unchanged.
sudo restorecon -Rv /srv/mysite
ls -Zd /srv/mysite
curl -sS -o /tmp/rhcsa-page -w '%{http_code}\n' http://localhost/
cat /tmp/rhcsa-page
Worth knowing

chcon would also have worked right now - and would be wiped by the next relabel. semanage fcontext writes the rule into policy; restorecon applies it. That pairing is the correct, persistent answer.

4. Port labels

First inspect existing port labels. A previously allowed port may not fail; adding an already defined port needs deliberate modification rather than -a.

Move httpd to port 8888
sudo semanage port -l | grep -E "8888|http_port_t"
sudo sed -i 's/^Listen 80$/Listen 8888/' /etc/httpd/conf/httpd.conf
sudo systemctl restart httpd   # may fail if the port is not allowed
sudo systemctl status httpd --no-pager | tail -5
Label the port, then it starts
sudo semanage port -l | grep -w http_port_t
# Inspect ALL policy labels for 8888. Then run exactly one appropriate command:
# Unassigned: sudo semanage port -a -t http_port_t -p tcp 8888
# Assigned to another type, after checking impact: sudo semanage port -m -t http_port_t -p tcp 8888
# Already http_port_t: no policy change is needed.
read -r -p 'Inspect the labels and apply the appropriate command in another console; Enter when done: ' _
sudo systemctl restart httpd
sudo firewall-cmd --get-active-zones
read -r -p 'Active lab-interface zone: ' WEBZONE
sudo firewall-cmd --permanent --zone="$WEBZONE" --add-port=8888/tcp
sudo firewall-cmd --reload
curl -sS -o /tmp/rhcsa-page -w '%{http_code}\n' http://localhost:8888/
cat /tmp/rhcsa-page

5. Booleans

Booleans switch predefined policy behaviour on and off. -P makes the change survive a reboot.

Find and set one
getsebool -a | head
getsebool -a | grep httpd | head -10
getsebool httpd_enable_homedirs
sudo setsebool -P httpd_enable_homedirs on
getsebool httpd_enable_homedirs
See what a boolean actually does
sudo semanage boolean -l | grep httpd_enable_homedirs
Worth knowing

Use -P for a persistent boolean change. Inspect current and persistent state and follow the requested target mode.

6. Read a denial

Being able to interpret the log is the skill; the fix follows from it.

Find and translate
sudo ausearch -m AVC -ts today 2>/dev/null | tail -20
sudo journalctl -t setroubleshoot --no-pager | tail
# sealert gives a plain-English explanation when setroubleshoot is installed:
sudo dnf install -y setroubleshoot-server 2>/dev/null
sudo sealert -a /var/log/audit/audit.log 2>/dev/null | head -30

7. Key-based SSH authentication

Generate a key and install it
ssh-keygen -t ed25519 -C 'shea@servera' -f ~/.ssh/id_ed25519 -N ''
ls -l ~/.ssh/
ssh-copy-id shea@serverb
ssh shea@serverb 'echo key auth works; hostname'
Confirm the permissions SSH insists on
ssh -o BatchMode=yes -o PasswordAuthentication=no shea@serverb 'echo key auth works; hostname'
ssh shea@serverb 'ls -ld ~/.ssh; ls -l ~/.ssh/authorized_keys'
# 700/600 are recommended; correct ownership and no unsafe write permissions matter.
Optionally disable password authentication
ssh -t shea@serverb
# In the remote shell, first keep this session open while testing another.
sudo tee /etc/ssh/sshd_config.d/00-rhcsa-auth.conf >/dev/null <<'EOF'
PasswordAuthentication no
EOF
sudo sshd -t
sudo sshd -T | grep '^passwordauthentication'
# If output still says yes, inspect earlier settings and Match blocks before proceeding.
sudo systemctl reload sshd
exit
ssh -o BatchMode=yes -o PasswordAuthentication=no shea@serverb 'hostname'

8. Default permissions with umask

See the effect
umask
touch ~/umask-default.txt
mkdir ~/umask-default-dir
ls -l ~/umask-default.txt
ls -ld ~/umask-default-dir
Change it for this shell, then persistently
umask 0077
touch ~/umask-private.txt
ls -l ~/umask-private.txt
echo 'umask 0077' >> ~/.bashrc
System-wide default
sudo tee /etc/profile.d/rhcsa-umask.sh >/dev/null <<'EOF'
umask 0077
EOF
su - shea -c 'umask; d=$(mktemp -d); touch "$d/file"; mkdir "$d/subdir"; ls -ld "$d/file" "$d/subdir"; rm -r "$d"'
# This profile controls login shells; services have separate UMask settings.
Worth knowing

umask clears permission bits from the requested mode; it is not arithmetic subtraction. 0077 gives 600/700; 0033 gives a normal new file 644. Use new files when testing.

Verify your work

Run these before you consider the lab finished.

  1. getenforce # must say Enforcing
  2. grep '^SELINUX=' /etc/selinux/config
  3. ls -Zd /srv/mysite | grep httpd_sys_content_t
  4. sudo semanage port -l | grep -w http_port_t | grep 8888
  5. getsebool httpd_enable_homedirs
  6. After a normal reboot, re-run the checks above
Break it, then fix it

Break:

sudo chcon -t user_home_t /srv/mysite/index.html && sudo restorecon -Rv /srv/mysite

What you'll see: You set a context with chcon, then restorecon immediately reverted it - because policy disagreed with you.

Fix:

The existing policy rule is already correct: sudo restorecon -Rv /srv/mysite. Use semanage fcontext -m only when an existing rule itself needs changing.

Why it matters: chcon changes the current label. restorecon and relabel apply policy; a reboot alone does not always undo chcon.

Now reboot

Run sudo reboot, then re-run every command in the verify list above. Check every persistent configuration after a normal boot. This is our practice validation, not an assertion about official exam scoring. Fix it now, while you can still see what you did.
